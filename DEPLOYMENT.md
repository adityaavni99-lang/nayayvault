# NAYAYVAULT

**Secure Digital Document Management System for Legal, Investigation, Court, and Forensic Documents**

## 🏛️ Tagline

**Secure. Traceable. Trusted.**

---

## 📋 Overview

NAYAYVAULT is a comprehensive full-stack hackathon prototype designed to demonstrate secure document management with:

✅ **SHA-256 Document Integrity Verification** - Every document receives a cryptographic hash generated by the Node.js backend  
✅ **Role-Based Access Control (RBAC)** - Four distinct user roles with granular permissions  
✅ **Tamper Detection** - Hash mismatch alerts when documents are modified  
✅ **Complete Auditability** - Append-only audit logs tracking all activities  
✅ **Version Control** - Document versions with tamper-evident chain  
✅ **Government-Style UI** - Professional, minimal, accessible interface  
✅ **Secure File Upload** - Backend validation and secure storage  

---

## 🎯 Core Features

### 1. **SHA-256 Document Integrity System**
- Every uploaded document automatically receives a SHA-256 cryptographic hash
- Hash is generated by Node.js backend using `crypto.createHash('sha256')`
- Hash is stored in PostgreSQL for later verification
- Enables tamper detection and document integrity verification

### 2. **Secure Document Upload Flow**
1. User authenticates
2. System verifies user role and permissions
3. User selects case and document metadata
4. Backend receives file securely
5. **Backend calculates SHA-256 hash** from actual file contents
6. Document ID is generated
7. File is stored securely
8. Metadata including SHA-256 hash is stored in database
9. Audit log entry is created
10. User receives confirmation with SHA-256 hash

### 3. **Document Integrity Verification**
When a user requests verification:
1. Backend retrieves the stored document
2. Calculates current SHA-256 hash from file contents
3. Compares with stored hash
4. Returns verification result (VERIFIED or MISMATCH)
5. Records verification in audit log
6. Alerts created if hash mismatch detected

### 4. **Role-Based Access Control**

| Feature | Investigator | Judge | Forensic | Lawyer |
|---------|-------------|-------|----------|--------|
| Upload Documents | ✓ | ✓ | ✓ | ✓ |
| View Authorized Docs | ✓ | ✓ | Limited | ✓ |
| Search Documents | ✓ | ✓ | Limited | ✓ |
| Verify Integrity | ✓ | ✓ | ✓ | ✓ |
| View Audit Logs | Limited | ✓ | Limited | Limited |
| Access All Documents | ✗ | ✓ | ✗ | ✗ |

### 5. **Supported Document Types**
- FIRs (First Information Reports)
- Police Reports
- Investigation Records
- Witness Statements
- Charge Sheets
- Court Filings
- Evidence Records
- Forensic Reports
- Legal Notices
- Court Judgments

## 🛠️ Database Schema

### Users Table
```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  user_id VARCHAR(50) UNIQUE NOT NULL,
  full_name VARCHAR(255) NOT NULL,
  email VARCHAR(255) UNIQUE NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  role VARCHAR(50) NOT NULL,
  department VARCHAR(100),
  is_active BOOLEAN DEFAULT true,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### Documents Table (with SHA-256)
```sql
CREATE TABLE documents (
  id SERIAL PRIMARY KEY,
  document_id VARCHAR(100) UNIQUE NOT NULL,
  case_id INTEGER REFERENCES cases(id),
  document_name VARCHAR(500) NOT NULL,
  document_type VARCHAR(100),
  description TEXT,
  classification_level VARCHAR(50),
  file_path VARCHAR(500),
  file_size BIGINT,
  sha256_hash VARCHAR(64) NOT NULL,  -- SHA-256 hash in hex
  version_number INTEGER DEFAULT 1,
  previous_version_hash VARCHAR(64),
  uploaded_by INTEGER REFERENCES users(id),
  uploaded_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  is_verified BOOLEAN DEFAULT false,
  last_verified_at TIMESTAMP,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### Audit Logs Table (Append-Only)
```sql
CREATE TABLE audit_logs (
  id SERIAL PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),
  user_role VARCHAR(50),
  action VARCHAR(100),
  document_id INTEGER REFERENCES documents(id),
  case_id INTEGER REFERENCES cases(id),
  details TEXT,
  ip_address VARCHAR(45),
  timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## 🔍 Testing SHA-256 Integrity

### Upload a Document
1. Login as any user
2. Go to "Upload Document"
3. Select a case, document type, and file
4. Submit the form
5. Backend generates SHA-256 hash
6. Document is securely stored
7. Hash is recorded in database

### Verify Document Integrity
1. Navigate to "Documents"
2. Click on a document
3. Click "Verify Document Integrity"
4. Backend recalculates current SHA-256 hash
5. Compares with stored hash
6. Shows verification result:
   - **VERIFIED**: Hashes match - document integrity confirmed
   - **HASH MISMATCH**: Hashes differ - document may have been tampered with

### Demo Tampering Detection
To demonstrate tampering:
1. Upload a document
2. Modify the file on disk
3. Click "Verify Document Integrity"
4. The hash will not match
5. System displays tampering alert
6. Audit log records the mismatch

## ⚠️ Security Considerations

1. **SHA-256 is for integrity, not password hashing**
   - Passwords use bcrypt (Argon2 recommended for production)
   - SHA-256 used only for document tampering detection

2. **Backend Authorization**
   - All protected endpoints verify JWT token
   - Role and case permissions checked server-side
   - Frontend cannot bypass authorization

3. **File Security**
   - Files stored outside web root
   - File type validation on backend
   - File naming randomized
   - Size limits enforced

4. **Audit Trail**
   - Append-only database design
   - Normal users cannot modify/delete logs
   - All sensitive actions recorded
   - IP addresses logged

5. **Encryption**
   - HTTPS recommended in production
   - JWT tokens expire after 24 hours
   - Secrets stored in environment variables
